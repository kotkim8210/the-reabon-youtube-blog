## 1. Problem Statement

농산물을 쿠팡·토스·태무 등 여러 채널에 파는 위탁셀러는 매일 **채널별 주문 엑셀을 내려받아 → 산지 거래처가 알아볼 양식으로 수작업 변환 → 거래처에 발주 → 회신받은 운송장을 다시 채널에 입력**하는 반복 작업에 묶여 있다. 품목(콜라비·참외·고구마 등)마다 옵션·등급·중량 표기가 다르고, 거래처마다 양식이 달라 엑셀 수작업에 하루 수 시간이 든다. 실수 시 오배송·정산 오류로 직결된다. 현재 이 문제를 한 번에 풀어주는 **농산물 산지직송 특화 발주 자동화 도구는 시장에 거의 없다.**

## 2. 타겟 고객 / 페르소나

| 페르소나 | 설명 | 핵심 니즈 |
|---|---|---|
| **P1. 농산물 멀티채널 셀러 (주 타겟)** | 쿠팡 로켓그로스/토스/태무에 제철 농산물을 위탁판매하는 1인~소상공인 | 주문→발주→운송장 왕복을 클릭 몇 번으로, 품목별 옵션 변환 자동화 |
| **P2. 소규모 농산물 유통업자** | 여러 산지 거래처와 다수 품목을 중개 | 거래처별 양식 관리, 공급가 변동(마진) 추적, 정산 |
| **P3. 일반 쿠팡 셀러 (확장)** | 비농산물 셀러 | 범용 발주서 변환 (품목 특화 로직 없이) |

**대표 페르소나는 P1.** 기존 기능(품목별 프로세서 25종)이 P1에 최적화돼 있다.

## 3. 핵심 가치 제안

- **"채널 주문 엑셀만 올리면, 거래처별 발주서와 운송장이 자동으로."**
- 멀티채널(쿠팡·토스·태무) 단일 워크플로우 통합
- 농산물 특화: 품목·등급·중량 옵션 변환 로직 내장 (범용 셀러툴과의 결정적 차별점)
- 마진방어(공급가 변동 추적) + 옵션별 판매·정산 추적 대시보드
- 미가공 농산물 면세 처리 등 도메인 규칙 반영

## 4. Goals (측정 가능한 목표)

1. **온보딩→첫 가치까지 시간 단축**: 신규 가입자가 가입 후 **10분 내 첫 발주서 생성** 성공 (현재는 셀러별 수동 셋업)
2. **수작업 시간 절감**: 핵심 워크플로우(주문→발주→운송장)를 건당 **수 시간 → 5분 이내**
3. **멀티테넌트 안전성**: RLS로 **타 테넌트 데이터 접근 0건** (보안 사고 0)
4. **유료 전환**: 출시 3개월 내 활성 사용자의 **유료(Pro) 전환율 15%+**
5. **처리 신뢰성**: 발주서/운송장 자동처리 **성공률 99%+** (매칭 실패는 명시적 표시)

---

## 5. Non-Goals (이번 범위 제외)

1. **네이버 스마트스토어/자사몰 API 직접 연동** — 가치 크지만 별도 이니셔티브(P2, `project_balju_api_future.md` 참조). v1은 쿠팡·토스·태무.
2. **자체 결제 PG 구축** — 토스페이먼츠 구독으로 충분. 직접 PG는 과잉.
3. **모바일 네이티브 앱** — 웹(반응형)으로 시작. 앱은 수요 검증 후.
4. **거래처(공급사)용 별도 포털** — v1은 셀러가 엑셀 파일로 거래처와 주고받는 현행 방식 유지.
5. **AI 기반 옵션 자동매핑(LoRA 등)** — R&D 자산은 있으나 v1은 규칙기반 변환으로 안정성 우선.

## 6. User Stories

### P1. 농산물 멀티채널 셀러
- 셀러로서, **쿠팡 DeliveryList 엑셀을 업로드**하면 거래처별 발주서가 자동 생성되길 원한다 — 수작업 변환을 없애기 위해.
- 셀러로서, **거래처 회신 엑셀(여러 개)을 한 번에 올려** 운송장이 주문에 자동 매칭되길 원한다 — 채널 입력 시간을 줄이기 위해.
- 셀러로서, **쿠팡 API로 운송장을 직접 등록**하고 싶다 — 채널 재업로드 단계를 없애기 위해.
- 셀러로서, **내 품목·거래처 양식을 직접 등록/수정**하고 싶다 — 신규 품목을 운영이 셀프로 추가하기 위해.
- 셀러로서, **공급가가 바뀌면 마진 영향을 한눈에** 보고 싶다 — 역마진을 막기 위해.
- 셀러로서, **옵션별 판매량·정산금 추이**를 보고 싶다 — 무엇이 팔리는지 알기 위해.

### 신규 가입자 (온보딩)
- 신규 사용자로서, **카카오/구글로 30초 안에 가입**하고 싶다 — 진입장벽을 낮추기 위해.
- 신규 사용자로서, **샘플 파일로 즉시 체험**하고 싶다 — 결제 전 가치를 확인하기 위해.

### 관리자 (운영)
- 운영자로서, **테넌트별 사용량·구독 상태**를 보고 싶다 — 과금/지원을 위해.
- 운영자로서, **테넌트 데이터가 RLS로 격리**되어 있음을 보장받고 싶다 — 보안 사고를 막기 위해.

## 8. 멀티테넌시 · 보안 (RLS)

- **격리 모델**: 모든 데이터 테이블에 `user_id`(또는 `tenant_id`) 컬럼 + **Postgres RLS 정책**으로 `auth.uid() = user_id` 강제.
- **현행 대비 개선**: 기존은 애플리케이션 쿼리(`WHERE user_id=?`)에만 의존 → 코드 실수 시 유출 위험. RLS는 **DB가 강제**하므로 이중 안전망.
- **서비스 롤 분리**: 백그라운드 작업(스케줄러, 쿠팡 캐시)은 service_role 키로 RLS 우회하되 코드에서 명시적 테넌트 스코프 적용.
- **민감정보**: 쿠팡 API 키, 토스 빌링키 등은 암호화 저장 + RLS 보호.
- **감사**: billing_events·usage_logs로 과금/접근 추적.

## 9. SQLite → Supabase 마이그레이션 단계

| Phase | 내용 | 산출물 / 완료 기준 |
|---|---|---|
| **0. 준비** | Supabase 프로젝트 생성, 28테이블 Postgres DDL 작성, RLS 정책 정의 | `supabase/schema.sql`, RLS 정책, 환경변수 셋업 |
| **1. 데이터 이전 스크립트** | SQLite→Postgres 덤프/변환(SQLite 특화 문법 제거: `INSERT OR IGNORE`→`ON CONFLICT`, PRAGMA/VACUUM 제거) | 무결성 검증 스크립트(행수·합계 대조), 스테이징 검증 통과 |
| **2. DB 레이어 교체** | `aiosqlite` → `asyncpg`/`supabase-py`, 50여 쿼리 함수 변환, 커넥션 풀 | 기존 테스트/수동 회귀 통과 |
| **3. Auth 전환** | 자체 JWT+OAuth → Supabase Auth, 기존 사용자 계정 매핑, 토큰 검증 미들웨어 교체 | 기존 사용자 재로그인 성공, 소셜 로그인 동작 |
| **4. Storage·컷오버** | 엑셀 파일 Storage 이관, 프로덕션 컷오버, 모니터링·롤백 플랜 | 다운타임 최소 컷오버, 24h 모니터링 |

> 각 Phase는 **스테이징에서 검증 후** 프로덕션 반영. Phase 1·3이 최고 리스크.

## 10. 비기능 요구사항 (NFR)

- **확장성**: Postgres 커넥션 풀, 동시 사용자 수백 대응. Fly 머신 수평 확장 가능 구조.
- **가용성**: Supabase 관리형 DB로 단일 SQLite 파일 단일장애점 제거. 목표 99.9%.
- **백업/복구**: Supabase 자동 백업(PITR). 복구 절차 문서화.
- **성능**: 발주서 생성 P95 < 5초(파일 크기 의존), 대시보드 조회 < 1초.
- **관측성**: 구조화 로깅, 처리 성공/실패 메트릭, 에러 알림.
- **데이터 규정**: 개인정보(수취인·연락처·주소) 최소 보관·암호화, 면세 농산물 정산 규칙 반영.

## 11. 요금제 전략 (4단 재설계 — 상세: [02-monetization-pricing.md](./02-monetization-pricing.md))

| 플랜 | 가격(월/연) | 한도 | 대상 |
|---|---|---|---|
| **Free** | ₩0 | 상품 1개, 월 50건 | 체험·초소형 |
| **Starter** | ₩19,000 | 상품 5개, 월 300건 (디코이) | 입문 셀러 |
| **Pro** ⭐가장 인기 | ₩39,000 (연 2개월 무료) | 무제한 상품, 월 3,000건, 전기능 | **주 타겟 P1** |
| **Business** | ₩99,000 (앵커) | 다중 사용자·우선지원·API | 유통업자 P2 |

- **앵커링**: Business를 상단 앵커, Starter를 디코이로 배치해 Pro를 "합리적 중간"으로 유도
- **그랜드페더링**: 기존 Pro ₩29,000 사용자는 가격 동결(인상 저항 차단)
- **전환 엔진**: 영구 Freemium + 사용량 페이월(월 한도 80%/95%/100% 업셀 트리거) + 신규 14일 Pro 체험
- **이탈 방지**: 해지 3단 흐름 + **구독 일시정지(최대 3개월)** — 농산물 비수기 이탈을 구조적으로 흡수
- **수익 시뮬레이션**: 보수/기본/공격 = MRR ₩1.57M / ₩4.46M / ₩12.6M (상세 02 문서)

> ⚠️ 기술부채: `config.py`의 `PRO_PLAN_PRICE` 하드코딩 → 다티어 대응 위해 `plans` 테이블 단가로 일원화 필요 (마이그레이션 시 처리).

| Auth 전환 시 기존 사용자 강제 재로그인 허용 범위 | 엔지니어링 | 블로킹(Phase 3 전) |
| 컷오버 시 허용 다운타임 (무중단 vs 점검창) | 엔지니어링 | 블로킹(Phase 4 전) |
| 개인정보 보관 기간·암호화 범위 (법적 검토) | 법무 | 블로킹(출시 전) |

## 14. Timeline / Phasing (제안)

- **Sprint 1–2**: Phase 0~1 (Supabase 스키마·RLS·데이터 이전 스크립트 + 스테이징 검증)
- **Sprint 3–4**: Phase 2 (DB 레이어 교체, 회귀 검증)
- **Sprint 5**: Phase 3 (Auth 전환)
- **Sprint 6**: Phase 4 (Storage·컷오버) + P1-1 온보딩
- **출시 후**: P1 나머지 → P2 로드맵

> 의존성: Phase 순차 진행. Phase 2는 Phase 1 검증 완료가 선행조건.

## 15. Risks & Mitigation

| 리스크 | 영향 | 완화 |
|---|---|---|
| 데이터 이전 누락/손상 | 치명 | 무결성 검증 스크립트, 스테이징 리허설, 롤백 백업 |
| RLS 정책 오류 (유출/접근불가) | 치명 | 정책 단위 테스트, 음성 테스트(타테넌트 차단 확인) |
| Auth 전환 시 로그인 끊김 | 높음 | 계정 매핑 사전 검증, 점진 전환, 안내 공지 |
| SQLite 특화 문법 변환 누락 | 중 | 쿼리 인벤토리 체크리스트, 자동 회귀 |
| 컷오버 다운타임 | 중 | 점검창 공지 or 듀얼라이트 무중단 전략 |
| 비용 초과(Supabase 성장) | 저 | 무료티어 시작, 사용량 모니터링, Pro 전환 시 상향 |
